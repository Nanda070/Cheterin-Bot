# Дашборд для Discord-бота — Фаза 4a: Обращения (Feedback/тикеты)

Дата: 2026-07-03
Статус: утверждено пользователем, готово к написанию плана реализации

## Контекст

Фазы 1, 2a, 2b, 3a, 3b завершены. Пункт сайдбара "Feedback и тикеты" сейчас
неактивен (плейсхолдер без `to`). Фаза 4 — это большая функция, разбитая на
суб-фазы по аналогии с Фазой 3:

- **Фаза 4a (эта)** — просмотр и принятие/отклонение обращений из дашборда.
- Фаза 4b (позже) — управление категориями обращений через дашборд (сейчас
  единственная категория `"players"` захардкожена в `feedback_menu.py`
  через `get_feedback_categories()`, настраивается только env-переменными).
- Фаза 4c (позже) — публикация панели обращений через дашборд (сейчас
  только через `/feedback_panel send`).

У бота уже есть полноценная система обращений в `feedback_menu.py`
(это и есть "тикеты" из исходного запроса пользователя): кнопка на панели →
модалка с полями → создаётся "дело" (case) — публичный трекер-эмбед в
целевом канале + приватный тред для staff с полной инфой и кнопками
"Принять"/"Отклонить". Решение обновляет оба эмбеда, шлёт DM автору,
закрывает и блокирует тред. Состояние — `bot.feedback_cases` (dict
`case_id -> dict`) и `bot.feedback_counters`, персистятся в общем
`invites_stats.json` через `bot.update_file()`.

## Данные и переиспользование логики

Текущая функция `close_case(interaction, bot, case_id, approved)` в
`feedback_menu.py` целиком завязана на объект `interaction` (для
`interaction.user`, `interaction.followup.send`, `interaction.channel`).
Чтобы дашборд мог вызывать тот же самый путь принятия решения без
дублирования логики (и не рисковать расхождением поведения, как чуть не
случилось с lockdown в Фазе 2a), логика выносится в новый файл
`feedback_core.py` (репозиторий, рядом с `lockdown_core.py`) — по тому же
паттерну: одна функция, которую вызывают и Discord-обработчик кнопки, и
роут дашборда.

**`async def decide_case(bot, guild, case_id: str, approved: bool, decided_by_id: int, decided_by_mention: str) -> dict`**
— не принимает `interaction`, только явные параметры вместо
`interaction.user`. Выполняет ровно то же самое, что сейчас делает
`close_case()`: обновление статуса в `bot.feedback_cases` + запись файла,
обновление публичного эмбеда, обновление эмбеда в треде (кнопки
дизейблятся), отправка DM автору обращения, публикация эмбеда-решения в
треде и его архивация+блокировка. Возвращает `{"ok": bool, "error": str |
None}` — `error` в `{"not_found", "already_decided"}` при ранних
отказах, иначе `None`.

Важное уточнение по поведению: в текущем коде публикация эмбеда-решения
и архивация треда происходят внутри блока
`if isinstance(interaction.channel, discord.Thread):` — на практике это
условие всегда истинно, когда кнопку нажимают из самого треда (кнопки
"Принять"/"Отклонить" живут только там), поэтому поведение бота не
меняется. В `decide_case()` этот блок становится безусловным и использует
уже полученный по `case_data["thread_id"]` объект треда напрямую — так
путь дашборда (без `interaction`) получает тот же результат.

`feedback_menu.py::close_case()` переписывается в тонкую обёртку: достаёт
`interaction.user.id`/`.mention`, вызывает `feedback_core.decide_case(...)`,
транслирует `error` в те же ephemeral-сообщения, что сейчас
(`"Обращение не найдено или уже закрыто."` и т.д.). Существующее поведение
бота не меняется ни в одном сценарии — это чистый рефакторинг с новым
дашборд-путём поверх общей логики.

## API дашборда

```
GET  /api/feedback-cases?status=pending       список, фильтр по статусу
GET  /api/feedback-cases/{case_id}            полная карточка
POST /api/feedback-cases/{case_id}/decide     {"approved": bool}
```

Все роуты — в новом `dashboard/backend/routes/feedback.py`, под
`@require_dashboard_access` (как все роуты предыдущих фаз).

**`GET /api/feedback-cases`** — `status` необязателен, допустимые значения
`pending`/`approved`/`denied` (без параметра — все статусы). Возвращает
`{cases: [{case_id, category_key, category_title, submitter_id,
submitter_display, status, created_at}]}`, отсортировано по `created_at`
по убыванию (новые сверху). `category_title` и поля резолвятся из
`feedback_menu.get_feedback_categories()[category_key]` — дашборд не
дублирует конфиг категорий, читает тот же source of truth, что и бот (это
автоматически подготавливает почву под Фазу 4b, где категории станут
редактируемыми — формат данных не изменится). `submitter_display` —
`guild.get_member(submitter_id).display_name`, либо сам ID строкой, если
участник уже покинул сервер (не считается ошибкой).

**`GET /api/feedback-cases/{case_id}`** — `404 not_found`, если
`case_id` отсутствует в `bot.feedback_cases`. При успехе — полная карточка:
все поля из `case_data` плюс расшифрованные ответы (нужно где-то их
хранить — см. ниже) плюс ссылки на публичное сообщение/тред
(`jump_url`-эквиваленты, собранные из `channel_id`/`message_id`).

**Важный пробел в текущих данных**: `create_feedback_case()` сейчас
сохраняет в `bot.feedback_cases[case_id]` только метаданные (`submitter_id`,
`category_key`, `status`, ID сообщений/треда) — **сами ответы из модалки
(`answers` dict) никуда не сохраняются**, они уходят только в эмбед в
треде. Чтобы дашборд мог показать содержимое обращения без похода в
Discord, `create_feedback_case()` дополняется одной строкой: сохранение
`answers` в `case_data["answers"]` при создании (обратной совместимости
не требуется — это новая фича, старых записей без `answers` в реальных
данных нет, но код на всякий случай отдаёт `{}` при отсутствии ключа для
уже существующих старых кейсов).

**`POST /api/feedback-cases/{case_id}/decide`** — тело `{"approved":
bool}`. Вызывает `feedback_core.decide_case(bot, guild, case_id, approved,
decided_by_id=<discord_user_id из сессии>, decided_by_mention=f"<@{id}>")`.
`decided_by_id` берётся из сессии (`request["discord_user_id"]`, тот же
паттерн, что во всех предыдущих Фазах для модератора/автора действия — не
из тела запроса). Ответ: `200 {"ok": true}` при успехе,
`404 {"error": "not_found"}` если кейса нет, `409 {"error":
"already_decided"}` если уже принято/отклонено (не `pending`).

## UI дашборда

Пункт сайдбара "Feedback и тикеты" получает `to: '/feedback'`.

**Список** (`FeedbackCasesPage`): таблица case_id / категория / отправитель
/ статус / дата, по паттерну списков из предыдущих фаз (`Card`-строки).
Фильтр по статусу — выпадающий список сверху
(`pending`/`approved`/`denied`/`все`), по умолчанию `pending`. Клик по
строке открывает детальную панель.

**Детальная панель** (`FeedbackCaseDetail`, модалка или боковая панель —
по паттерну `MemberDetailPanel` из Фазы 2a): заголовок категории и номер
дела, отправитель (кликабельный переход в участника — опционально,
не обязательно для v1), все поля ответов (label из конфига категории +
значение), ссылки на публичное сообщение и тред, кнопки "Принять"/
"Отклонить" (задизейблены, если статус уже не `pending`, с текстом
"Уже рассмотрено — <статус>").

## Обработка ошибок

Единообразно с предыдущими фазами: `404` для отсутствующего `case_id`,
`409` для попытки повторно решить уже закрытое дело (вместо тихого
игнорирования, как сейчас в Discord-пути, где просто шлётся ephemeral-
сообщение — дашборду нужен структурированный код ошибки для UI).
Сбои отдельных шагов внутри `decide_case()` (не удалось отправить DM,
не удалось обновить публичный эмбед и т.д.) — как и сейчас в
`close_case()`, логируются и не прерывают остальные шаги (DM — best-effort,
это уже так в существующем коде и не меняется).

## Вне рамок этой фазы

- Управление категориями (создание/редактирование категорий, полей формы,
  каналов/ролей-ревьюеров через дашборд) — Фаза 4b.
- Публикация панели обращений через дашборд — Фаза 4c.
- Изменение уже одобренного кода `feedback_menu.py` за пределами
  описанного рефакторинга (`close_case()` → тонкая обёртка над
  `feedback_core.decide_case()`, плюс сохранение `answers` в
  `create_feedback_case()`).
- Причина отклонения (текстовое поле при "Отклонить") — сейчас в Discord
  её тоже нет, дашборд не добавляет то, чего нет в боте.
