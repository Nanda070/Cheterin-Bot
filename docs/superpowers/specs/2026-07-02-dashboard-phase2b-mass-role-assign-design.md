# Дашборд для Discord-бота — Фаза 2b: Массовая выдача ролей

Дата: 2026-07-02
Статус: утверждено пользователем, готово к написанию плана реализации

## Контекст

Фаза 2a (участники, бан/кик, одиночная роль, lockdown) завершена и одобрена
(`docs/superpowers/specs/2026-07-01-dashboard-phase2a-members-moderation-design.md`).
Фаза 2b — вторая половина исходного пункта "выдача ролей" из брейнштрома Фазы 2:
массовая выдача **одной** роли группе участников (по выбору / всем / всем кроме ботов).
Массовое **снятие** роли не запрашивалось — не реализуется (YAGNI).

Переиспользуется без изменений: `require_dashboard_access` (Фаза 2a),
`_resolve_assignable_role`/`GET /api/roles` (роль должна быть ниже роли бота, не
`@everyone`/`managed`), `dashboard_reason(...)`, дизайн-система (Card/Button/Dropdown/
Modal, токены Tailwind v4), `GET /api/members` (поиск участников — переиспользуется
внутри модалки для режима "по выбору").

## Модель выполнения

Операция может занять минуты на большом сервере (рейт-лимиты Discord). Выполняется как
**фоновая asyncio-задача в том же процессе бота** — без БД, очередей или WebSocket.
Состояние джобы хранится **в памяти** (`dict[str, MassAssignJob]` на уровне модуля),
не переживает перезапуск бота — это приемлемо для внутреннего инструмента модерации.

**Одновременно разрешена только одна активная джоба.** Повторный запрос во время
выполнения → `409 {"error": "job_already_running"}`. Это упрощает UI (не нужен список
джоб) и исключает гонки при параллельных массовых операциях.

На рейт-лимиты Discord API отдельно не влияем — полагаемся на встроенный лимитер/бэкофф
`discord.py`. Используем `asyncio.Semaphore(3)` вокруг вызовов `add_roles`, чтобы не
запускать сотни параллельных корутин разом (экономия памяти/сокетов), но не пишем
собственный throttling поверх библиотечного.

## API

```
POST /api/roles/{role_id}/mass-assign
  body: {"target": "all" | "all_except_bots" | "selected", "member_ids"?: string[]}
  -> 202 {"job_id": string}
  -> 400 если target="selected" и member_ids пуст/отсутствует
  -> 403/404 если роль не назначаема (переиспользует _resolve_assignable_role)
  -> 409 если уже есть активная джоба

GET /api/roles/mass-assign/{job_id}
  -> 200 {
       "status": "running" | "completed" | "failed",
       "total": int,
       "processed": int,
       "succeeded": int,
       "skipped": int,      # уже была роль — не трогаем повторно
       "failed": int,
       "errors": [string]   # до 20 последних, "{имя}: {причина}"
     }
  -> 404 если job_id неизвестен
```

`target="all"` — все участники гильдии (включая ботов, если явно не исключены —
буквально "всем участникам"). `target="all_except_bots"` — фильтр `not member.bot`.
`target="selected"` — только переданные `member_ids`, каждый валидируется как реальный
участник гильдии (пропускается с ошибкой в `errors`, если не найден).

## Выполнение джобы

Модуль `dashboard/backend/mass_role_jobs.py`:

```python
@dataclass
class MassAssignJob:
    status: str  # "running" | "completed" | "failed"
    total: int
    processed: int = 0
    succeeded: int = 0
    skipped: int = 0
    failed: int = 0
    errors: list[str] = field(default_factory=list)

JOBS: dict[str, MassAssignJob] = {}

async def run_mass_assign(job_id, guild, role, member_ids, moderator) -> None:
    ...
```

`processed` инкрементируется на каждого обработанного участника независимо от исхода,
поэтому всегда верно `processed == succeeded + skipped + failed` в любой момент; когда
`processed == total`, джоба переходит в `status="completed"`.

`run_mass_assign` — чистая корутина, не зависящая от aiohttp `request` (тестируется
через прямой `await`, без фоновых таймеров — по опыту Фазы 2a: избегать
`vi.useFakeTimers()`-подобных паттернов там, где можно просто `await` до конца).
Для каждого участника: если роль уже есть → `skipped += 1`; иначе `add_roles(role,
reason=dashboard_reason(...))` под семафором; `discord.HTTPException` на конкретном
участнике → `failed += 1` + запись в `errors`, **не прерывает** обработку остальных.
После завершения статус → `"completed"` (даже если часть участников упала — это не
фейл всей операции; `"failed"` статус джобы зарезервирован под фатальные ошибки типа
исчезновения гильдии/роли до начала обработки).

Роут `POST .../mass-assign` создаёт `job_id = str(uuid4())`, кладёт начальный
`MassAssignJob(status="running", total=len(targets))` в `JOBS`, запускает
`asyncio.create_task(run_mass_assign(...))` (fire-and-forget, ошибки внутри уже
обрабатываются самой корутиной) и сразу возвращает `202` с `job_id`.

## Фронтенд

Новый `dashboard/frontend/src/components/MassAssignModal.tsx` — не трогает `Members.tsx`
напрямую, только добавляет туда одну кнопку "Массовая выдача роли" рядом с поиском,
открывающую модалку. Внутри модалки:

1. Выбор роли — `Dropdown` со списком из `GET /api/roles` (переиспользуется).
2. Радио-выбор таргета: "Выбранные участники" / "Все участники" / "Все кроме ботов".
3. Для "Выбранные" — собственное поле поиска (переиспользует `fetchMembers`) со
   списком чекбоксов и счётчиком "Выбрано: N".
4. После запуска — экран прогресса: `processed/total`, обработанных/успешно/пропущено/
   ошибок, список последних ошибок. Опрос статуса каждые 2 сек через `setInterval`
   (реальное время, без fake timers — тесты используют `waitFor`).
5. По завершении — итоговая сводка, кнопка "Готово" закрывает модалку и обновляет
   список участников на фоне (как в Фазе 2a).

## Обработка ошибок

- Роль не назначаема / участник не найден → как в Фазе 2a (403/404/503).
- `target="selected"` с несуществующим `member_id` → не блокирует всю операцию,
  попадает в `errors` джобы как "Участник {id}: не найден на сервере".
- Повторный запуск во время активной джобы → `409`, фронтенд показывает "Уже
  выполняется массовая операция, дождитесь завершения".
- Опрос несуществующего `job_id` (например, после перезапуска бота, когда джоба
  пропала из памяти) → `404`, фронтенд показывает "Информация о задаче недоступна"
  вместо бесконечного спиннера.

## Тестирование

Как в Фазе 2a: pytest + существующие fakes (`FakeGuild`/`FakeMember`/`FakeRole`) для
`run_mass_assign` (прямой `await`, без реальных задержек) и для роутов (immediate 202 +
job_id, 409 на дубль, polling статуса). Frontend — Vitest, `waitFor` с реальным
временем для опроса прогресса.

## Вне рамок этой фазы

- Массовое **снятие** роли (не запрашивалось).
- Персистентность джоб между перезапусками бота.
- Несколько параллельных джоб одновременно.
- Любые изменения в уже одобренном коде Фаз 1/2a, кроме одной новой кнопки в
  `Members.tsx` и регистрации новых роутов в `create_app`.
