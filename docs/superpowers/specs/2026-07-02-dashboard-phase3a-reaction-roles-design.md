# Дашборд для Discord-бота — Фаза 3a: Reaction Roles

Дата: 2026-07-02
Статус: утверждено пользователем, готово к написанию плана реализации

## Контекст

Фазы 1 (Фундамент) и 2 (2a — участники/модерация, 2b — массовая выдача ролей) завершены
и одобрены. Фаза 3 изначально задумывалась как "конструктор кнопок и эмбедов"
(discohook-style). Пользователь запросил добавить перед этим отдельную функцию —
**Reaction Roles** (выдача роли по реакции-эмодзи на сообщение), управляемую через
дашборд, по референсу интерфейса ProBot/Carl (адаптировано под нашу дизайн-систему,
без концепции "Message type" — упрощено до одного фиксированного поведения).

У бота этой функции сейчас нет вообще — реализуется с нуля и в самом боте
(`on_raw_reaction_add`/`on_raw_reaction_remove`), и в дашборде. По объёму это
самостоятельная, хорошо ограниченная подсистема, поэтому выделена в отдельную фазу
**3a**, отдельно от **3b** (конструктор эмбедов/кнопок, будет спроектирован позже).
Пункт сайдбара "Конструктор кнопок и эмбедов" становится рабочей ссылкой на
`/reaction-roles` — первая функциональная часть этого раздела; остальное (Фаза 3b)
добавится туда же позже.

Существующий паттерн в кодовой базе, на который эта фаза опирается по структуре:
`button.py` (JSON-конфиг `buttons_config.json`, `_load/_save` хелперы, toggle-выдача
роли через `add_roles`/`remove_roles`, лог-эмбеды в `LOG_CHANNEL_ID`). Reaction Roles —
концептуально похожая, но отдельная механика Discord (реакции на сообщения, а не клики
по компонентам), поэтому не переиспользует код `button.py` напрямую, но следует тем же
конвенциям (JSON-хранилище, стиль логирования, формат причин).

## Модель данных

Новый файл `reaction_roles.py` (репозиторий, рядом с `button.py`/`lockdown_core.py`).
Конфиг `reaction_roles.json`, ключ — `message_id` (естественный первичный ключ: одно
сообщение = одна reaction-role панель):

```json
{
  "123456789012345678": {
    "channel_id": "987654321098765432",
    "pairs": [
      {"emoji": "📖", "role_id": "111111111111111111"},
      {"emoji": "<:custom_name:222222222222222222>", "role_id": "333333333333333333"}
    ]
  }
}
```

`emoji` хранится строкой: unicode-символ как есть, кастомный эмодзи сервера — в
Discord-формате `<:name:id>` (или `<a:name:id>` для анимированных). Сравнение с
`payload.emoji` при обработке реакции — по значению `str(payload.emoji)`, которое
discord.py формирует в этом же формате для обоих типов, так что сравнение единообразно.

**Публичные функции модуля** (переиспользуются и ботом, и дашбордом):
`load_config()`, `save_config(data)`, `get_pairs_for_message(message_id) -> list | None`.

## Бот-логика: слушатели реакций

Новый ког `ReactionRoles` (или функции в `reaction_roles.py`, подключаемые в `main.py`
через `setup_hook`, как остальные коги):

- `on_raw_reaction_add(payload)` / `on_raw_reaction_remove(payload)` — **raw**-версии
  обязательны, так как реакции могут ставиться на сообщения вне кэша бота.
- Игнорируются реакции самого бота (`payload.user_id == self.bot.user.id`).
- Ищем `str(payload.message_id)` в конфиге; если не найдено — выходим сразу (частый
  путь, должен быть дешёвым).
- При совпадении эмодзи в списке пар: `add`-событие → `member.add_roles(role,
  reason=...)`; `remove`-событие → `member.remove_roles(role, reason=...)`. Поведение
  фиксированное (toggle) — без конфигурируемого "типа", как и просил пользователь.
  **Важная деталь discord.py:** `payload.member` доступен только в
  `on_raw_reaction_add` (Discord включает объект участника в это событие); в
  `on_raw_reaction_remove` его нет — участника нужно резолвить самостоятельно через
  `guild.get_member(payload.user_id)` с фолбэком на `guild.fetch_member(...)`
  (аналогично `resolve_guild_member` из Фазы 1, но без необходимости импортировать
  dashboard-код — достаточно инлайн той же логики или прямого вызова
  `guild.fetch_member`).
- Причина для Discord API и лог-эмбед в `LOG_CHANNEL_ID` — по конвенции существующего
  кода (`f"Reaction role: {action} — by reaction on message {message_id}"`).
- **Самопроверка при старте** (в `setup()` кога): для каждого `message_id` в конфиге
  пытаемся `channel.fetch_message(message_id)`; если `discord.NotFound` — запись тихо
  удаляется из конфига (самовосстановление после ручного удаления сообщения в Discord).

## API дашборда

```
GET    /api/reaction-roles                  список конфигов
POST   /api/reaction-roles                  создать
PUT    /api/reaction-roles/{message_id}     редактировать (только pairs)
DELETE /api/reaction-roles/{message_id}     удалить
GET    /api/emojis                          кастомные эмодзи сервера (для пикера)
```

Все роуты — в новом `dashboard/backend/routes/reaction_roles.py`, под
`@require_dashboard_access` (как все роуты Фаз 2a/2b). Роли для пикера — из уже
существующего `GET /api/roles` (Фаза 2a), новый эндпоинт под это не нужен.

**`GET /api/reaction-roles`** → `{reaction_roles: [{message_id, channel_id, pairs:
[{emoji, role_id}]}]}` — сырой список из конфига, обогащение именами ролей/каналов
делает фронтенд (уже имеет данные ролей из `GET /api/roles`, каналы можно резолвить
на бэкенде по аналогии — см. ниже).

**`POST /api/reaction-roles`** — тело `{channel_id, message_id, pairs: [{emoji,
role_id}]}`. Валидация по порядку:
1. `pairs` не пустой.
2. Внутри `pairs` нет повторяющихся `emoji` (иначе `400 duplicate_emoji`) — иначе
   неоднозначно, какую роль выдавать при реакции.
3. Канал существует на сервере (`guild.get_channel`) → иначе `404 channel_not_found`.
4. Сообщение существует в канале (`channel.fetch_message(message_id)`, не полагаемся на
   кэш) → `discord.NotFound` → `404 message_not_found`.
5. Каждая роль — назначаема (та же проверка "не `@everyone`/`managed`/выше роли бота",
   что в `_resolve_assignable_role` Фазы 2a; неназначаемая роль в `pairs` → `403
   role_not_assignable`, дальше не идём).

При успехе: сохраняем в конфиг, затем **бот проставляет свои реакции**
(`message.add_reaction(emoji)` на каждую пару). Ошибка простановки одной реакции
(например, кастомный эмодзи оказался невалиден к моменту вызова) — логируется, не
прерывает сохранение остальных пар (конфиг уже сохранён, частичная простановка реакций
не блокирует создание записи).

**`PUT /api/reaction-roles/{message_id}`** — тело `{pairs: [...]}` (без
`channel_id`/`message_id` — смена целевого сообщения означает по сути новую панель:
удалить и создать заново). Та же валидация пунктов 1-2-5. Синхронизация реакций на
сообщении: снимает реакции бота для пар, которых больше нет в новом списке
(`message.remove_reaction(emoji, bot.user)`), добавляет реакции для новых пар. Ошибки
синка отдельных реакций — логируются, не блокируют сохранение конфига (конфиг —
источник истины, реакции на сообщении — визуальное отражение).

**`DELETE /api/reaction-roles/{message_id}`** — удаляет запись из конфига, best-effort
снимает реакции бота с сообщения (если сообщение уже удалено — `discord.NotFound`
игнорируется, конфиг всё равно чистится).

**`GET /api/emojis`** → `{emojis: [{id, name, url}]}` — `guild.emojis`, только реально
существующие на сервере кастомные эмодзи (невалидные/удалённые эмодзи в принципе не
могут туда попасть — источник данных сам по себе исключает их).

## Обработка ошибок (сводно)

- Канал/сообщение не найдены → `404` с понятным `error`-кодом (см. выше).
- Роль выше роли бота / `@everyone`/`managed` → не отображается в пикере ролей
  (переиспользует уже отфильтрованный `GET /api/roles`); на бэкенде дополнительно
  `403`, если клиент всё же прислал такую роль напрямую.
- Дубли эмодзи внутри одной панели → `400` при создании/редактировании, до любых
  вызовов Discord API.
- Сообщение удалено между созданием конфига и следующей синхронизацией/стартом бота →
  запись автоматически удаляется (см. "Бот-логика").
- Ошибка простановки/снятия отдельной реакции (гонка, невалидный эмодзи, права) →
  логируется, не блокирует остальную операцию.
- `discord.Forbidden` на любом Discord-вызове → `403` с понятным текстом (у бота
  Administrator, поэтому на практике маловероятно, но не должно приводить к падению).

## UI дашборда

Пункт сайдбара "Конструктор кнопок и эмбедов" → рабочая ссылка на `/reaction-roles`.

**Список** (`ReactionRolesPage`): таблица Канал / Роли (превью через запятую,
резолвится из уже загруженного `GET /api/roles`) / Действия (Edit, Delete с
подтверждением через `Modal`, по паттерну Фазы 2a). Кнопка "Создать reaction role"
открывает форму создания.

**Форма создания/редактирования** (`ReactionRoleForm`, отдельный компонент/модалка):
- Канал (select) и Message ID (текст) — при создании редактируемые, при
  редактировании — `disabled`/только для чтения.
- Список пар эмодзи↔роль: каждая пара — эмодзи-пикер (текстовое поле для unicode ИЛИ
  выбор из кастомных эмодзи сервера через `GET /api/emojis`, переключение похожим
  паттерном, что таргет-режимы в `MassAssignModal` из Фазы 2b) + роль-дропдаун (данные
  из `GET /api/roles`) + кнопка удаления пары. Кнопка "+ добавить пару" добавляет
  пустую пару в конец списка.
- Клиентская валидация перед отправкой: хотя бы одна пара, нет повторяющихся эмодзи
  внутри списка (дублирует серверную проверку для мгновенной обратной связи).

## Тестирование

Как в Фазах 2a/2b: pytest + существующие fakes (`FakeGuild`/`FakeMember`/`FakeRole`) +
новые `FakeChannel`/`FakeMessage` (с `fetch_message`, `add_reaction`,
`remove_reaction`, поднимающими `discord.NotFound`/`discord.HTTPException` по
необходимости) — и для роутов дашборда, и для самих обработчиков
`on_raw_reaction_add/remove` (вызываются напрямую с сконструированным
`RawReactionActionEvent`-подобным объектом, без реального Discord gateway). Frontend —
Vitest, по паттерну `MassAssignModal`/`MemberDetailPanel`.

## Вне рамок этой фазы

- Ограничения по ролям на получение реакции-роли (allow-list/blacklist ролей, как в
  референсе ProBot) — явно отложено пользователем, YAGNI для v1.
- Бот не составляет сообщение сам — только привязка к уже существующему `message_id`
  (в отличие от `button.py`, который создаёт сообщение с кнопками). Автопостинг может
  быть добавлен отдельной задачей позже, если понадобится.
- Любые изменения в уже одобренном коде Фаз 1/2 — эта фаза только добавляет новые
  файлы и один пункт сайдбара (переиспользует существующие `GET /api/roles`,
  `require_dashboard_access`, дизайн-систему).
