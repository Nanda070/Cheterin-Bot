Дата: 2026-07-01

## Контекст

Фаза 1 (Фундамент — сервер, OAuth2, каркас) завершена, проверена и одобрена
(`docs/superpowers/specs/2026-07-01-dashboard-phase1-foundation-design.md`,
план `docs/superpowers/plans/2026-07-01-dashboard-phase1-foundation.md`). Поверх неё

Фаза 2 по исходному разбиению — "Модерация участников" (бан/кик, инфо, роли в т.ч.
массовая выдача, lockdown). Массовая выдача ролей архитектурно сильно отличается от
остального (потенциально долгая фоновая операция с прогрессом, батчинг из-за
рейт-лимитов Discord API), поэтому Фаза 2 разбита на два цикла:

- **Фаза 2a (этот документ):** поиск/список участников, карточка участника, бан, кик,
  выдача/снятие **одной** роли, lockdown on/off/status.
- **Фаза 2b (отдельный спек позже):** массовая выдача ролей (по выбору/всем/всем кроме
  ботов) — фоновое исполнение с прогрессом.

## Существующий функционал бота (переиспользуется, не дублируется)

У бота **нет** команд `/ban`, `/kick` или ручной выдачи ролей — бан/роли сейчас
происходят только автоматически (антиспам, кнопки-роли, авто-tempban по каналу). Для
дашборда переиспользуются:

- **`/userinfo`** (`welcome.py`) — набор полей карточки участника: дата входа, дата
  регистрации, роли, инвайт-статистика (`bot.stats`), количество жалоб
  (`bot.feedback_cases`). Dashboard-эндпоинт карточки участника отдаёт те же поля.
- **`Lockdown`-ког** (`lockdown.py`) — логика `_activate`/`_deactivate`/`_status`
  переиспользуется через рефакторинг (см. ниже), а не дублируется.
- **Формат причины и логирования** (`spam.py`, `tempban.py`) — действия из дашборда
  логируются в `LOG_CHANNEL_ID` через существующий `bot.send_log(embed)`, причина в
  Discord API формируется как `f"Dashboard: {reason} — by {moderator.name}
  ({moderator.id})"`, тем же паттерном, что уже используется в `spam.py`.

## API-поверхность

Новые роуты в `dashboard/backend/routes/moderation.py` (участники/бан/кик/роли) и
`dashboard/backend/routes/lockdown.py` (антиспам-режим) — используют заготовленную в
Фазе 1 структуру `dashboard/backend/routes/`.

```
GET    /api/members?search=&page=&page_size=   поиск + список участников
GET    /api/members/{id}                        карточка участника
POST   /api/members/{id}/ban                     бан
POST   /api/members/{id}/kick                    кик
GET    /api/roles                                назначаемые роли
POST   /api/members/{id}/roles                   выдать роль
DELETE /api/members/{id}/roles/{role_id}          снять роль
GET    /api/lockdown/status                      статус антиспам-режима
POST   /api/lockdown/activate                    включить
POST   /api/lockdown/deactivate                  выключить
```

## Access control: `@require_dashboard_access`

В Фазе 1 проверка "сессия → участник → права" была инлайнена в каждый роут (`callback`,
`me` в `auth.py`). Копировать этот блок в 6+ новых роутов — нарушение DRY, поэтому
выносится в переиспользуемый декоратор `dashboard/backend/access_middleware.py`:

```python
@require_dashboard_access
async def handler(request: web.Request) -> web.Response:
    moderator = request["moderator"]  # discord.Member, уже проверенный
    ...
```

Декоратор внутри выполняет ту же последовательность, что и `me()` в Фазе 1: читает
`discord_user_id` из сессии (401 если нет), `resolve_guild_member` (503 при сбое кэша
бота, 403 если участник не найден), `has_dashboard_access` (403 если роли/права не
подходят) — и только при успехе кладёт найденного `discord.Member` в
`request["moderator"]` и вызывает обёрнутый хендлер. Существующие роуты Фазы 1 (`me`,
`callback`) **не переписываются** на декоратор — они уже прошли ревью и работают,
трогать их вне рамок этой фазы нецелесообразно. Декоратор применяется только к новым
роутам Фазы 2a.

## Участники: поиск, карточка, бан, кик

**`GET /api/members`** — фильтрует `guild.members` (уже в кэше бота благодаря
`intents.members=True`, без обращения к Discord API) по подстроке, регистронезависимо,
проверяя совпадение и с `member.name` (логин), и с `member.display_name` (никнейм на
сервере, если задан) — участник находится по любому из двух. Пустой/отсутствующий
`search` → возвращает первую страницу без фильтра. Пагинация — срез отфильтрованного
списка (без внешней БД: сервер не рассчитан на сотни тысяч участников);
`page` по умолчанию `1`, `page_size` по умолчанию `20` (максимум `100`, чтобы нельзя
было запросить весь список одним запросом). Ответ — лёгкие карточки: `id`, `username`,
`avatar`, `role_count`, `joined_at`, плюс `total` (общее число совпадений) для пагинации
на фронте.

**`GET /api/members/{id}`** — полная карточка, поля идентичны `/userinfo`: `id`,
`username`, `avatar`, `joined_at`, `created_at` (оба — ISO 8601 строки), `roles`
(список `{id, name, color}`, `color` — hex-строка вида `#5865f2`, `"#000000"` если у
роли нет цвета), `invite_stats` (`{joins, leaves, invites}` из `bot.stats`),
`feedback_case_count` (из `bot.feedback_cases`), `is_bot`.

**`POST /api/members/{id}/ban`** — тело `{reason: string, delete_message_days: 0|1|7}`.
`reason` обязателен (валидация на бэкенде, не только на фронте). `delete_message_days`
маппится в `delete_message_seconds` (Discord API). Подтверждение перед действием — на
фронте (модалка), бэкенд просто исполняет запрос.

**`POST /api/members/{id}/kick`** — тело `{reason: string}`, аналогично.

**Ошибки:** `discord.Forbidden` (бот не может забанить/кикнуть — например, роль цели
выше роли бота) → `403` с понятным текстом; `discord.NotFound` (участник уже не на
сервере на момент действия) → `404`; прочие `discord.HTTPException` → `502` с логом на
сервере.

## Роли

**`GET /api/roles`** — список ролей, которые можно назначать: `role.position <
guild.me.top_role.position`, исключая `@everyone` и `role.managed` (интеграционные/
буст-роли — их и так нельзя назначить вручную через Discord API).

**`POST /api/members/{id}/roles`** — тело `{role_id: string}`, вызывает
`member.add_roles(role, reason=...)`.
**`DELETE /api/members/{id}/roles/{role_id}`** — `member.remove_roles(role,
reason=...)`.

Если роль всё же оказалась выше бота на момент запроса (рассинхрон кэша между
`GET /api/roles` и действием) — Discord API вернёт `Forbidden`, обрабатывается так же,
как в бане/кике: `403` с понятным текстом, не падение.

## Lockdown: рефакторинг существующего кога

`_activate`/`_deactivate`/`_status` в `lockdown.py` сейчас жёстко завязаны на
`discord.Interaction` (используют `interaction.followup.send(...)`), поэтому напрямую
из aiohttp-роута их не вызвать. Основная логика (обход ролей сервера, сохранение
бэкапа, применение/откат изменений) выносится в чистые функции без зависимости от
`Interaction`:

```python
async def activate_antispam(
    guild: discord.Guild, mention_exempt: set[int], mentionable_exempt: set[int]
) -> tuple[int, list[str]]:  # (modified_count, errors)
    ...

async def deactivate_antispam(guild: discord.Guild) -> tuple[int, list[str]]:
    ...

def antispam_status() -> tuple[bool, int]:  # (is_active, role_count)
    ...
```

Существующая slash-команда `/antispam` и новые dashboard-роуты
(`GET/POST /api/lockdown/*`) оба вызывают эти функции — единая логика, без риска
расхождения между Discord-командой и веб-интерфейсом. Slash-команда после рефакторинга
берёт результат и форматирует в embed (как сейчас), dashboard-роуты — в JSON.

## Фронтенд

В сайдбаре `DashboardShell` два плейсхолдера становятся рабочими ссылками:
"Участники и роли" → `/members`, "Lockdown и модерация" → `/lockdown`. Остальные 4
раздела остаются заглушками "скоро" — вне рамок этой фазы.

- **`/members`** — поиск + постраничный список карточками (дизайн-система Фазы 1: `Card`,
  токены). Клик по участнику открывает панель с карточкой-инфо и кнопками
  Бан/Кик (модалка подтверждения + поле причины, для бана — выбор 0/1/7 дней) и
  `Dropdown`-пикером ролей (назначить/снять).
- **`/lockdown`** — карточка со статусом антиспам-режима и кнопками Включить/Выключить.

## Обработка ошибок (сводно)

- Нет/просрочена сессия → `401`, фронтенд редиректит на логин (как в Фазе 1).
- Роли/права не подходят или участник не найден в кэше/API → `403`/`404` (через
  `@require_dashboard_access`).
- Кэш бота временно недоступен → `503` (как в Фазе 1).
- Discord отклонил действие (иерархия ролей, права бота) → `403` с текстом причины.
- Участник пропал с сервера между поиском и действием → `404`.
- Прочие ошибки Discord API → `502`, подробности в серверный лог.

## Тестирование

Та же схема, что в Фазе 1: TDD с pytest, фейковые `Guild`/`Member`/`Role`-объекты (по
образцу `FakeGuild`/`FakeMember` из тестов auth.py) для бэкенда — без реальных вызовов
Discord API. Frontend — Vitest для логики поиска/пагинации и сценариев подтверждения
действий (модалки бан/кик).
