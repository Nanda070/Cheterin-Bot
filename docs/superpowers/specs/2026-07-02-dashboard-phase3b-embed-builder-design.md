# Дашборд для Discord-бота — Фаза 3b: Конструктор эмбедов

Дата: 2026-07-02
Статус: утверждено пользователем, готово к написанию плана реализации

## Контекст

Фаза 3a (Reaction Roles) завершена. Фаза 3 изначально задумывалась как единый
"конструктор кнопок и эмбедов" (discohook-style); в ходе работы над ней была
выделена отдельная функция Reaction Roles (3a), а сам конструктор
сообщений/эмбедов стал Фазой **3b** — она добавляется поверх уже
существующего пункта сайдбара "Конструктор кнопок и эмбедов", который сейчас
ведёт на `/reaction-roles`.

Навигация: страница `/reaction-roles` получает **вкладки** — "Reaction
Roles" (существующий контент Фазы 3a без изменений) и "Эмбеды" (новый
контент Фазы 3b). URL не меняется, переключение — на клиентском состоянии.

Существующий паттерн в кодовой базе, на который эта фаза опирается:
`button.py` уже умеет создавать сообщения с "роль-кнопками" —
`/button_create role` отправляет сообщение с рядом до 5 кнопок, каждая
переключает (toggle) роль по нажатию. Эти кнопки **полностью без хранения
состояния**: `custom_id` кнопки сам кодирует `role_id`
(`btn_role_{role_id}`), и `on_interaction`-обработчик в `button.py` парсит
его напрямую — никакого конфиг-файла для роль-кнопок не существует и не
нужно. Фаза 3b переиспользует эту же схему `custom_id`, чтобы дашборд мог
прикреплять роль-кнопки к составленным эмбед-сообщениям **без каких-либо
изменений в `button.py`** — его обработчик продолжит работать как есть.

Второй тип кнопок в `button.py` — "кнопки-формы" (модальное окно с
вопросами, ответ уходит в вебхук) — **в эту фазу не входит**, остаётся
доступным только через slash-команду.

## Модель данных

**Никакого нового JSON-конфига не заводится** — фича полностью без
хранения состояния, по аналогии с роль-кнопками `button.py`. Создание
нового сообщения и редактирование уже отправленного работают одинаково:
сотрудник указывает канал и (для редактирования) ID сообщения напрямую —
тот же UX-паттерн, что и "привязка к существующему ID" в Reaction Roles
(Фаза 3a).

Новый файл `embed_builder.py` (репозиторий, рядом с `reaction_roles.py` и
`button.py`) — **только чистые функции, без кога и без слушателей**:

- `build_embed(spec: dict) -> discord.Embed` — собирает `discord.Embed` из
  JSON-спеки формы.
- `embed_to_spec(embed: discord.Embed) -> dict` — обратное преобразование,
  для подгрузки текущего содержимого при редактировании.
- `build_role_button_view(guild, role_ids: list[int]) -> discord.ui.View` —
  собирает `discord.ui.View` с кнопками в точности как
  `button.py::_create_role` (тот же `custom_id` формат
  `btn_role_{role_id}`, `ButtonStyle.secondary`, label = имя роли, до 5
  кнопок).
- `parse_role_button_ids(message: discord.Message) -> list[int]` —
  обратное преобразование: проходит по `message.components`, вытаскивает
  `role_id` из кнопок с `custom_id`, начинающимся на `btn_role_`;
  остальные кнопки (например, руками добавленные или кнопки-формы) молча
  игнорируются.
- `validate_embed_spec(spec: dict) -> str | None` — структурная валидация
  без обращений к Discord API, возвращает код ошибки или `None`:
  - хотя бы одно из полей `title`/`description`/`fields`/`image`/`thumbnail`
    заполнено (Discord отклоняет полностью пустой эмбед);
  - `title` ≤ 256 символов;
  - `description` ≤ 4096 символов;
  - `footer.text` ≤ 2048 символов;
  - `author.name` ≤ 256 символов;
  - `fields` ≤ 25 штук, каждое `name` ≤ 256 / `value` ≤ 1024 символов;
  - суммарный "бюджет" символов (title + description + footer.text +
    author.name + все fields.name/value) ≤ 6000 — реальный лимит Discord.

**Форма спеки эмбеда** (единая структура и во фронтенд-состоянии формы, и
в теле API-запроса):

```json
{
  "title": "Заголовок",
  "description": "Текст описания",
  "url": "https://example.com",
  "color": "#5865F2",
  "author": {"name": "...", "url": "...", "icon_url": "..."},
  "footer": {"text": "...", "icon_url": "..."},
  "image": {"url": "..."},
  "thumbnail": {"url": "..."},
  "timestamp": "2026-07-02T12:00:00Z",
  "fields": [{"name": "...", "value": "...", "inline": true}]
}
```

Одно сообщение — один эмбед (без multi-embed, YAGNI для v1). Опциональный
обычный текст сообщения (`content`) хранится отдельно от эмбеда, как в
discohook.

## API дашборда

```
POST   /api/embed-messages                              отправить новое
GET    /api/embed-messages/{channel_id}/{message_id}     загрузить для редактирования
PUT    /api/embed-messages/{channel_id}/{message_id}     сохранить изменения
```

Все роуты — в новом `dashboard/backend/routes/embed_builder.py`, под
`@require_dashboard_access`. Списки для пикеров переиспользуются из уже
существующих `GET /api/channels` (Фаза 3a) и `GET /api/roles` (Фаза 2a) —
новых эндпоинтов под это не требуется.

**Тело `POST`/`PUT`:** `{content: string | null, embed: {...спека выше},
role_ids: string[]}` (`role_ids` — до 5 штук, кнопки роль-toggle).

**Порядок валидации** (по аналогии с исправленным в Фазе 3a порядком —
структурные проверки без Discord-вызовов идут первыми, ресурсоёмкие/
Discord-зависимые — последними):

1. `validate_embed_spec(spec)` → `400 invalid_embed`.
2. `len(role_ids) <= 5` → `400 too_many_roles`.
3. Канал существует (`guild.get_channel`) → `404 channel_not_found`.
4. *(только для `GET`/`PUT`)* сообщение существует
   (`channel.fetch_message`) → `404 message_not_found`.
5. Каждая роль в `role_ids` — назначаема (не `@everyone`, не `managed`,
   позиция ниже роли бота — та же проверка, что в Фазах 2a/3a) →
   `403 role_not_assignable`.
6. Вызов Discord API (`channel.send(...)` для `POST`,
   `message.edit(...)` для `PUT`) — при `discord.HTTPException` лог через
   `logger.warning` (по конвенции, закреплённой в финальном ревью Фазы 3a)
   и `502 discord_error` клиенту.

**`POST` при успехе** → `201 {message_id, channel_id}`.
**`PUT` при успехе** → `200 {message_id, channel_id}`.
**`GET` при успехе** → `200 {content, embed: {...спека}, role_ids:
string[]}` — `embed` собирается через `embed_to_spec(message.embeds[0])`
(если эмбедов нет — все поля спеки пустые), `role_ids` — через
`parse_role_button_ids(message)`.

## UI дашборда

Страница `/reaction-roles` (переименование URL не требуется) получает
вкладки над текущим контентом:
- **"Reaction Roles"** — существующая страница Фазы 3a без изменений.
- **"Эмбеды"** — новый контент Фазы 3b.

**Вкладка "Эмбеды"** (`EmbedBuilderPage` + `EmbedBuilderForm`):
- Переключатель режима: "Новое сообщение" / "Редактировать существующее".
- Режим редактирования: канал (select) + Message ID (текст) + кнопка
  "Загрузить" → вызывает `GET`, заполняет всю форму ниже текущим
  содержимым сообщения.
- Режим создания: канал (select, обязателен).
- Поля формы: текст сообщения (textarea, опционально), затем поля эмбеда —
  title, description, URL, цвет (color-picker + hex-поле), author
  (name/url/icon URL), footer (text/icon URL), image URL, thumbnail URL,
  чекбокс "текущее время" (заполняет `timestamp`), список полей `fields[]`
  (name/value/inline-чекбокс, до 25, кнопка "+ добавить поле" — тот же
  паттерн повторяемого списка, что и пары эмодзи↔роль в
  `ReactionRoleForm` из Фазы 3a).
- Пикер роль-кнопок: мульти-select из уже загруженного списка ролей
  (Фаза 2a), до 5 штук.
- **Живой превью**: панель, стилизованная под настоящую карточку эмбеда
  Discord (цветная полоса слева, строка author с иконкой, жирный title,
  description, сетка полей с учётом `inline`, image, thumbnail, footer с
  иконкой и временем) — чистый презентационный React-компонент
  (`EmbedPreview`), обновляется на каждое изменение состояния формы, без
  обращений к бэкенду.
- Клиентская валидация перед отправкой дублирует `validate_embed_spec`
  (лимиты символов, обязательность хотя бы одного поля) для мгновенной
  обратной связи.
- Кнопка сохранения: "Отправить" (создание) / "Сохранить" (редактирование).

## Обработка ошибок

Те же конвенции, закреплённые в Фазе 3a: структурные `400` до любых
обращений к Discord; `404` для отсутствующего канала/сообщения; `403` для
неназначаемой роли; ошибки самого вызова отправки/редактирования —
`logger.warning` на сервере + понятный `502` клиенту (не проглатывается
молча — конвенция из финального ревью Фазы 3a).

pytest + существующие fakes из `dashboard/backend/tests/fakes.py`,
расширенные `FakeChannel.send(...)` и `FakeMessage.edit(...)` (сейчас их

`parse_role_button_ids`. Frontend — Vitest, по паттерну
`ReactionRoleForm`/`ReactionRolesPage` из Фазы 3a.

## Вне рамок этой фазы

- Кнопки-формы (вебхук-опросники) — остаются только через slash-команду
  `button.py`.
- Множественные эмбеды в одном сообщении.
- Список/история эмбед-сообщений, созданных через дашборд (без хранения
  состояния — редактирование требует знания канала и ID сообщения).
- Смешивание роль-кнопок и кнопок-форм в одном сообщении.
- Отложенная/запланированная отправка.
- Любые изменения в уже одобренном коде Фаз 1-3a кроме: новых файлов,
  небольшого рефакторинга существующей страницы `/reaction-roles` в
  два таба (перенос текущего JSX в отдельный компонент-вкладку без
  изменения его логики).
