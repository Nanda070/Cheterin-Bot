# Дашборд для Discord-бота — Фаза 4b: Категории обращений

Дата: 2026-07-03
Статус: утверждено пользователем, готово к написанию плана реализации

## Контекст

Фаза 4a (просмотр и принятие/отклонение обращений) завершена. Категории
обращений сейчас полностью захардкожены в
`feedback_menu.py::get_feedback_categories()` — функция с глобальным
кэшем, вычисляется один раз при первом вызове, читает 2 обязательные
env-переменные (`CHANNEL_COMPLAINT_PLAY`, `ROLE_PLAYERS`) и возвращает dict
с ОДНОЙ категорией `"players"`. Фаза 4b переносит хранение категорий в
JSON-конфиг, редактируемый через дашборд, по аналогии с
`reaction_roles.json`.

## Хранение

Новый файл `feedback_categories.py` (репозиторий, рядом с
`feedback_core.py`) — JSON-конфиг `feedback_categories.json`
(`{category_key: {...}}`), **без кэширования** (в отличие от текущего
`_feedback_categories_cache`) — это осознанное изменение: чтобы правки из
дашборда применялись немедленно, без перезапуска бота, конфиг читается с
диска при каждом вызове, как и `reaction_roles.json`.

**Публичные функции:** `load_categories() -> dict`, `save_categories(data:
dict) -> None`, `migrate_from_env_if_needed() -> None` — при отсутствии
`feedback_categories.json` и наличии env-переменных
`CHANNEL_COMPLAINT_PLAY`/`ROLE_PLAYERS`, создаёт файл с одной категорией
`"players"`, воспроизводящей текущий хардкод один в один (сохраняя
`case_prefix: "PR"`, чтобы существующие обращения и счётчик
`bot.feedback_counters["PR"]` продолжили работать без разрыва нумерации).
После этого env-переменные для категорий больше не читаются никогда.
Вызывается один раз при старте бота (в `main.py`'s `setup_hook`, до
загрузки `feedback_menu`) — если файл уже существует, ничего не делает.

`feedback_menu.py::get_feedback_categories()` сохраняет ровно то же имя
и путь импорта (нулевые изменения в `feedback_core.py`'s локальном
импорте и `dashboard/backend/routes/feedback.py`'s bare-импорте из Фазы
4a) — но становится тонкой обёрткой: `return
feedback_categories.load_categories()`. Модуль-уровневая переменная
`_feedback_categories_cache` и функция `_env_int` удаляются как более не
нужные.

## Модель данных категории

```json
{
  "players": {
    "title": "Жалоба на участника",
    "button_label": "Жалоба на участника",
    "channel_id": "987654321098765432",
    "case_prefix": "PR",
    "case_title": "Жалоба на участника",
    "thread_name": "player-report",
    "review_role_ids": ["111111111111111111"],
    "approved_text": "Участник наказан.",
    "denied_text": "Жалоба отклонена.",
    "modal_title": "Жалоба на участника",
    "fields": [
      {"key": "offender", "label": "Ник / ID участника", "style": "short", "required": true, "max_length": 120},
      {"key": "complaint", "label": "Суть жалобы", "style": "paragraph", "required": true, "max_length": 1000}
    ],
    "mini_summary_key": "offender"
  }
}
```

`button_style` (сейчас всегда `discord.ButtonStyle.secondary`) остаётся
фиксированной константой в коде, не редактируется через дашборд — она
никогда не варьировалась и в текущей единственной категории (YAGNI).
`review_user_ids` (прямое упоминание конкретных пользователей-ревьюеров,
не через роль) — вне рамок Фазы 4b: сейчас в реальных данных всегда
пустой список, дашборд поддерживает только выбор ролей-ревьюеров.
`style` в полях модалки хранится как строка `"short"`/`"paragraph"`
(вместо `discord.TextStyle.short/paragraph`) — конвертируется в
Discord-enum в `feedback_menu.py` в точке использования (`FeedbackModal`).

## Валидация

Общий паттерн — структурные проверки (без обращений к Discord) идут
первыми, затем проверки, требующие реального состояния сервера:

1. `key` — уникален среди категорий, соответствует `^[a-z0-9_]+$`, 1-32
   символа. Неизменяем после создания (как `message_id` в Reaction
   Roles) — смена ключа means удалить и создать заново.
2. `case_prefix` — уникален среди ВСЕХ категорий (иначе две категории
   разделят один счётчик `bot.feedback_counters[prefix]`, что создаст
   путаницу в нумерации дел), 1-6 символов, только заглавные латинские
   буквы и цифры.
3. `title`, `button_label`, `case_title`, `modal_title` — непустые,
   ≤ 80 символов (с запасом под лимиты Discord на заголовки/лейблы
   кнопок).
4. `thread_name` — непустой, ≤ 80 символов (оставляет место под суффикс
   `-{case_id}`, при том что реальный лимит имени треда в Discord — 100
   символов).
5. `fields` — от 1 до 5 штук (лимит Discord на поля в модалке), каждое:
   `key` уникален внутри категории, `label` непустой ≤ 45 символов
   (лимит Discord на лейбл `TextInput`), `max_length` от 1 до 4000,
   `style` — `"short"` или `"paragraph"`.
6. `mini_summary_key` — должен совпадать с `key` одного из полей в этой
   же категории.
7. `channel_id` — резолвится в реальный канал сервера (`404
   channel_not_found`, если нет).
8. `review_role_ids` — каждый резолвится в реальную роль сервера (`404`
   при отсутствии; без проверки иерархии — эти роли только для
   уведомлений/добавления в тред, не для выдачи прав).

## API дашборда

```
GET    /api/feedback-categories                     список
POST   /api/feedback-categories                     создать
PUT    /api/feedback-categories/{category_key}       редактировать
DELETE /api/feedback-categories/{category_key}
```

Все роуты — в `dashboard/backend/routes/feedback.py` (тот же файл, что
Фаза 4a — те же роуты для обращений уже там), под
`@require_dashboard_access`. Переиспользует `GET /api/channels` (Фаза
3b) и `GET /api/roles` (Фаза 2a) для пикеров.

**`DELETE`** — удаляет категорию без проверки на существующие обращения
этой категории. Уже существующие дела с этим `category_key` продолжат
отображаться в списке обращений (Фаза 4a) — `serialize_case_detail`/
`serialize_case_summary` уже умеют деградировать при неизвестном
`category_key` (показывают сырой ключ вместо заголовка, пустой список
полей) — это подтверждённое, безопасное поведение из финального ревью
Фазы 4a, не требует изменений.

## UI дашборда

Страница `/feedback` получает вкладки (тот же паттерн, что `/reaction-
roles` из Фазы 3b): **"Обращения"** (существующий контент Фазы 4a без
изменений) и **"Категории"** (новый контент Фазы 4b).

**Вкладка "Категории"**: список категорий (`Card`-строки: заголовок,
`case_prefix`, канал, количество полей) с кнопками Edit/Delete
(подтверждение через `Modal`, паттерн Фазы 3a), кнопка "Создать
категорию" открывает форму. Форма: `title`, `button_label`, `case_title`,
`modal_title`, `thread_name`, `case_prefix`, канал (select из `GET
/api/channels`), роли-ревьюеры (мульти-select из `GET /api/roles`),
`approved_text`/`denied_text`, список полей модалки (повторяемый
блок — `key`, `label`, `style` short/paragraph, `required`, `max_length`,
до 5 штук, паттерн "+ добавить поле" как в Reaction Roles/Embed
Builder), выбор `mini_summary_key` из уже введённых полей. `key`
категории — отдельное текстовое поле при создании (обязательное,
валидируется на фронтенде под `^[a-z0-9_]+$`), недоступно для
редактирования при правке существующей категории (как канал/ID
сообщения в Reaction Roles).

## Обработка ошибок

Единообразно с предыдущими фазами: `400` для структурных нарушений (до
любых обращений к Discord), `404` для несуществующего канала/роли/
категории (при `PUT`/`DELETE`), `409` при попытке создать категорию с
уже занятым `key` или `case_prefix`.

## Тестирование

pytest + существующие fakes (`FakeChannel`, `FakeRole`, `FakeGuild`) для
`feedback_categories.py` (CRUD + миграция) и роутов. Frontend — Vitest,
по паттерну `ReactionRoleForm`/`EmbedBuilderForm` (повторяемый список
полей, пикеры канала/ролей).

## Вне рамок этой фазы

- `review_user_ids` (прямые упоминания пользователей-ревьюеров без
  роли) — дашборд поддерживает только роли.
- Настройка `button_style` через дашборд — остаётся фиксированной
  константой.
- Автоматическое обновление уже опубликованной панели при
  редактировании категории (кнопки на уже отправленном сообщении
  панели не меняются сами — это ограничение Discord-сообщений,
  существовавшее и до этой фазы; повторная публикация через `/
  feedback_panel send` остаётся штатным способом обновить панель).
  Публикация панели через дашборд — Фаза 4c.
- Любые изменения в уже одобренном коде Фазы 4a за пределами описанного
  рефакторинга `get_feedback_categories()` в тонкую обёртку.
